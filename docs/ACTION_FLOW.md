# 玩家行动与主持节奏（1.2.12）

在冒险日志展开“行动队列”，可以看到正在处理谁、排队行动、等待的玩家、
失败原因及恢复操作。不是仅按一条“处理中”状态猜测主持是否工作。

## 两种节奏

- **逐人处理**：兼容现有行为，每条提交独立排队。
- **全员收集后联合处理**：房主在队列的“设置行动节奏”选择1–12位真人参与者，
  每人提交一条行动。未齐前不会生成可领取的主持回合；齐后形成一个 `kind:group` 联合回合。

仅内置／外部自动主持且开启自动排队可启用收集。更换节奏或名单前必须先处理当前排队、
失败及未封口的行动，避免把已经提交的内容丢在旧模式。
群聊 @主持人同样遵循收集规则；普通闲聊仍不触发。
收集中单独通用掷骰会保留结果，但不会绕过收集抢先创建主持回合。

到齐后下一轮开始收集，上一轮可以正在处理，页面会同时显示轮次及队列。
不自动设置收集超时。成员离队或长期未提交时会列为等待；房主可点击“提前结束本轮收集”，
明确确认只处理已提交者，未提交者跳过本轮，软件不替其选择行动。

## 行动补充

自己的行动在尚未领取或正在收集时可追加最多5次补充，每次1–1000字。
补充作为新日志事件保存，不改写原行动，不新建主持回合。其他人和智能体不能代补。
领取与补充在事务中校验；已领取／完成后返回409，请提交新行动。

## 联合回合接口

`claim.context.turn_actions` 包含每条玩家行动：

```json
[
  {"event_id":51,"user_id":2,"actor":"玩家A","content":"查看石门","supplements":[{"event_id":52,"content":"同时留意脚印"}]},
  {"event_id":53,"user_id":3,"actor":"玩家B","content":"询问守夜人","supplements":[]}
]
```

`turn.event_id` 仅为本回合首条触发事件，不代表全部玩家。
**每项检定必须传入对应行动的 `event_id`，角色user_id必须匹配该行动user_id。**
同一租约可处理本联合回合的各条行动，不能处理下一轮或别的回合。
内置工具和新版 `campaign-agent.cjs` 已支持可选event_id；旧外部主持应更新后再使用联合模式。
旧主持在逐人模式仍可继续使用原complete接口。

公开模型上下文不会夹带后续已排队批次、尚未收齐的新一轮及其补充；正式日志仍保留所有成员可见行动。
随机点数／资源结算沿用原有幂等规则，重试不会把联合回合拆成多次重投。

## HTTP

路径相对 `/api/v1/campaigns/{id}`：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/flow` | 成员／本战役令牌读节奏、排队与等待状态，不含秘密／lease |
| PUT | `/flow` | 房主设置 `{client_id,version,mode:"individual"或"collect",participants:[用户id]}` |
| POST | `/flow/release` | 房主提前结束 `{client_id,version,allow_missing:true}` |
| POST | `/actions/{event}/supplement` | 行动本人追加 `{client_id,content}` |

收集释放、补充和节奏设置均有幂等回执；相同编号和相同内容重试不重复创建回合。
失败显示真实安全提示；外部主持可在fail请求附 `reason`：
`connection`、`model_response`、`tool_error`、`cancelled`、`unknown`。
不要把原始供应商报文、密钥或租约当作错误说明发送。
房主可重试并保留已掷骰，或明确跳过；等待代价选择必须由角色本人确认。
